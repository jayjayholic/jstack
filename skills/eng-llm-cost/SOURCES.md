# Sources: LLM cost, metering, keys and caching

Carried over from the research pass of 2026-10-25 (`02-research-llm-cost.md`), product-specific lines removed. Each line keeps the tag it had there: **[V]** checked against the primary page in that pass; **[K]**, **[B]**, **[C]** or **[M]** a known citation (author, year, venue) not re-opened; **[U]** unverified, treat as a hypothesis. Lines without a tag were cited with their venue and date only.

- S4 - Google SRE Workbook **"Alerting on SLOs"** (multiwindow, multi-burn-rate) - 2018 - [V] - burn-rate alerts 14.4 / 6 / 1 on 1h / 6h / 3d windows, each paired with a short window

- S6 - J. Chhabra, **"Caching challenges and strategies"**, Amazon Builders' Library - 2019 - [V] - soft/hard TTL, negative caching, request coalescing, a TTL chosen on purpose

- S8 - Anthropic, **Prompt caching** docs (platform.claude.com/docs/en/build-with-claude/prompt-caching) - 2026 - [V] re-read 2026-10-26 - request-level `cache_control` (automatic caching) "applies the cache breakpoint to the last cacheable block"; prefix order `tools` -> `system` -> `messages`, a change at one level invalidates it and every later level; minimum cacheable length per model (512, 1,024, 2,048 or 4,096 tokens), "Shorter prompts cannot be cached, even if marked", processed without caching and no error; writes 1.25x base input (5-minute TTL) or 2x (1-hour TTL), reads 0.1x (some models lower); `usage.cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` sum to `cache_creation_input_tokens`; 20-position lookback per breakpoint; unstable JSON key order breaks caches; a cache entry is readable only after the first response starts (parallel calls each write)
- S9 - OpenAI, **Prompt caching** guide (developers.openai.com/api/docs/guides/prompt-caching) - 2026 - [V] re-read 2026-10-26 - minimum 1,024 tokens on current models; `cached_tokens` counts billed reads, writes reported apart as `cache_write_tokens`; writes 1.25x (30 min) or 2.5x (12 h) on current models, reads 0.1x; `prompt_cache_key`; static content first, timestamps and user-specific content last
- S10 - Anthropic, **Token counting** + **Message Batches** docs (platform.claude.com) - 2026 - [V] - free `count_tokens` estimate before sending, batch at 50% price

- S12 - OpenTelemetry **GenAI semantic conventions** (`gen_ai.usage.input_tokens`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.usage.cache_creation.input_tokens`, `gen_ai.provider.name`, `gen_ai.request.model`; status *Development*) - 2025–26 - [V] attribute names and the Anthropic mapping (opentelemetry.io/docs/specs/semconv/gen-ai/anthropic). - S26 - Anthropic, **Context editing** docs (platform.claude.com/docs/en/build-with-claude/context-editing) - 2026 - [V] 2026-10-26 - tool-result clearing "Invalidates cached prompt prefixes when content is cleared"; `clear_at_least` "Ensures a minimum number of tokens is cleared each time the strategy activates ... helps determine if context clearing is worth breaking your prompt cache"; `trigger` (default 100,000 input tokens) and `keep` (default 3 tool uses). The basis for clearing with hysteresis
- S27 - Break-even of a cache write, derived from S8's multipliers: a 5-minute write costs 0.25x extra and each read saves 0.9x, so reads per written token must exceed 0.25 / 0.9 = 0.28; a 1-hour write needs 1 / 0.9 = 1.11. Models with cheaper reads move it slightly lower. `tools/unslop/cache-probe.mjs` uses it
- S28 - Anthropic, **Message Batches** (platform.claude.com/docs/en/build-with-claude/batch-processing) - 2026 - [V] 2026-10-26 - "well-suited to tasks that do not require immediate responses, with most batches finishing in less than 1 hour while reducing costs by 50%"; "limited to either 100,000 Message requests or 256 MB in size, whichever is reached first"; "Batches expire if processing does not complete within 24 hours"; "Batch results are available for 29 days"; "Batch results can be returned in any order ... always use the `custom_id` field"; expired requests "You will not be billed"; use cases: large-scale evaluations, content moderation, data analysis, bulk content generation; `max_tokens: 0` (pre-warming) rejected inside a batch
- S29 - Anthropic, **Prompt caching with Message Batches** (batch-processing page and the prompt-caching FAQ) - 2026 - [V] 2026-10-26 - "The pricing discounts from prompt caching and Message Batches can stack"; "cache hits are provided on a best-effort basis. Users typically experience cache hit rates ranging from 30 percent to 98 percent"; "consider using the 1-hour cache duration ... because batches can take longer than 5 minutes"; FAQ recipe: send one request with the shared prefix and a 1-hour cache block, then "As soon as this is complete, submit the rest"; prompt caching: "These multipliers stack with other pricing modifiers such as the Batch API discount"
- S30 - Anthropic, **Prompt caching**, re-read 2026-10-26 for layout and TTL - [V] - "You can define up to 4 cache breakpoints"; "The system checks at most 20 positions for each breakpoint"; "If a growing conversation pushes your breakpoint 20 or more blocks past the last write, the lookback window misses it. Add a second breakpoint"; minimum cacheable length 512 tokens on the newest models, 1,024, 2,048 or 4,096 on others; 5-minute vs 1-hour: keep 5 minutes for prompts "used more frequently than every 5 minutes, ... refreshed at no additional charge", 1 hour for prompts used "less frequently than every 5 minutes, but more frequently than every hour"; "Cache entries with longer TTL must appear before shorter TTLs"; "a cache entry only becomes available after the first response starts. If you need cache hits for parallel requests, wait for the first response"; caches isolated per workspace (Claude API) and never shared across organizations; `input_tokens` counts only tokens after the last breakpoint
- S31 - Anthropic, **Tool use with prompt caching** (platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching) - 2026 - [V] 2026-10-26 - modifying tool definitions invalidates tools, system and messages; changing `tool_choice`, `disable_parallel_tool_use` or toggling images invalidates the messages cache; thinking parameters and effort: messages always, tools and system on some models; `defer_loading` keeps the prefix untouched
- S32 - Anthropic, **Thinking and prompt caching** (platform.claude.com/docs/en/build-with-claude/thinking) - 2026 - [V] 2026-10-26 - "Switching between adaptive, enabled, and disabled, changing budget_tokens, and changing the effort value all invalidate cache breakpoints: message-level breakpoints always miss"; "Blocks passed back unchanged keep the cache intact"; "Thinking-heavy tasks often take longer than the default 5-minute cache lifetime ... Consider the 1-hour cache duration"; context editing: cleared thinking blocks invalidate the cache "at the point where clearing occurs", `keep: "all"` "maximizes cache hits"
- S33 - Anthropic, **Token counting** (platform.claude.com/docs/en/build-with-claude/token-counting) and **Compaction at a token threshold** - 2026 - [V] 2026-10-26 - token counting "is free to use but subject to requests per minute rate limits"; "The token count is an estimate"; it does not use caching; newer tokenizers count "approximately 30 percent more tokens" for the same text, so recount per model. Compaction: a breakpoint at the end of the system prompt keeps it cached, "Only the compaction summary needs to be written as a new cache entry"
- S34 - Break-even of the 1-hour TTL against the 5-minute one, derived from S8/S30: for k reuses that each land 5-60 min after the previous use, 5-minute costs 1.25(k + 1) (every reuse rewrites) and 1-hour costs 2 + 0.1k, so 1-hour is cheaper when k > 0.65, i.e. from one late reuse per hour. In a batch the same multipliers apply to the halved price (S29)
