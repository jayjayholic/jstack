# Sources: Security and secrets

Carried over from the research pass of 2026-10-25 (`02-research-security.md`), product-specific lines removed. Each line keeps the tag it had there: **[V]** checked against the primary page in that pass; **[K]**, **[B]**, **[C]** or **[M]** a known citation (author, year, venue) not re-opened; **[U]** unverified, treat as a hypothesis. Lines without a tag were cited with their venue and date only.

- A. Authorization not enforced on every path - 1, 2, 4, 8 - **Complete mediation**: "every access to every object must be checked for authority" (Saltzer & Schroeder, *The Protection of Information in Computer Systems*, Proc. IEEE 63(9), 1975)
- B. Protocol implemented partially - 3 - Follow the current protocol BCP verbatim, not a tutorial (IETF RFC 9700 / BCP 240, Jan 2025)
- C. Unsafe resource/defaults - 5, 7 - **Fail-safe defaults** (Saltzer & Schroeder 1975); **Secure by Default** (CISA with U.S. and international partner agencies, *Shifting the Balance of Cybersecurity Risk*, Apr 2023, revised 25 Oct 2023)
- D. Secret exposure + no per-change review - 6, 9, 10 - NIST SP 800-218 SSDF v1.1 (Feb 2022) practices PW.7 (review code), PS.1 (protect all forms of code; secrets only by extension), PO.5 (secure environments), RV; Microsoft SDL; OWASP ASVS 5.0 (30 May 2025)
- **Method:** Object-level authorization on every data access keyed by a client-supplied ID (OWASP API Security Top 10 **API1:2023 BOLA**; CWE-639 *Authorization Bypass Through User-Controlled Key*; OWASP Top 10 2021 **A01 Broken Access Control**). Design-time: tenant isolation as an invariant enforced at one choke point (row-level policy / scoped repository / ORM policy layer) rather than per handler — the "centralized authorization" pattern of Google Zanzibar (Pang et al., USENIX ATC 2019) and NIST SP 800-207 Zero Trust (Aug 2020, "per-request access decision").
- **When:** Before (threat model: STRIDE "Information disclosure / Elevation of privilege" per data-flow element — Kohnfelder & Garg, Microsoft 1999; Shostack, *Threat Modeling: Designing for Security*, Wiley 2014). During (write the query through the scoped accessor). After (cross-tenant test).
- **Sources:** Saltzer & Schroeder 1975; OWASP API Security Top 10 2023 (owasp.org/API-Security); CWE-639; Pang et al. 2019; NIST SP 800-207 (2020).
- **Method:** **Function-level authorization** with deny-by-default (OWASP API5:2023 *Broken Function Level Authorization*; CWE-862 *Missing Authorization*, CWE-863 *Incorrect Authorization*). Policy decision point (PDP) separate from enforcement point (PEP) — NIST SP 800-207 (2020); ASVS 5.0 chapter V8 *Authorization* (requires documented authorization rules + enforcement at trusted service layer).
- **Route inventory diff:** enumerate all procedures/routes (static AST or router introspection) and assert each one is either in an explicit `PUBLIC_ALLOWLIST` or calls the permission resolver. A new route with neither fails CI. (Pattern = "architecture fitness function", Ford, Parsons & Kua, *Building Evolutionary Architectures*, O'Reilly 2017.)
- **Property-based matrix test** (QuickCheck, Claessen & Hughes, ICFP 2000): generate random (role, permission set, scope, action) tuples; property: `allowed(action) ⇔ permissionSet grants action within scope`. Catches both under- and over-grant.
- **Sources:** OWASP API Top 10 2023; CWE-862/863; NIST SP 800-207; OWASP ASVS 5.0 (released 30 May 2025, Global AppSec EU); Claessen & Hughes 2000.
- **Method:** Implement against **RFC 9700 OAuth 2.0 Security BCP (BCP 240, Jan 2025)**: exact redirect-URI matching against pre-registered values; no open redirectors on client or AS; CSRF protection on the redirection endpoint via PKCE (RFC 7636, 2015) or one-time `state` bound to the user agent (or OIDC `nonce`); mix-up defense via `iss` (RFC 9207, 2022) when talking to multiple AS. For MCP servers (HTTP transports; authorization is OPTIONAL in MCP, but when supported): the MCP authorization spec (2025-06-18, built on the OAuth 2.1 draft) makes the server an OAuth 2.1 resource server; clients MUST send the RFC 8707 `resource` parameter in authorization and token requests and MUST implement PKCE; servers MUST validate that the token's audience is themselves and MUST NOT pass tokens through to upstream APIs; authorization servers MUST match redirect URIs exactly against pre-registered values; clients SHOULD use and verify `state`; 403 for invalid scopes (spec text opened this pass). Open redirect = CWE-601; OWASP *Unvalidated Redirects and Forwards Cheat Sheet*.
- Test pattern (redirects): every `returnTo|redirect|next|callbackUrl` param fed `https://evil.example`, `//evil.example`, `/\evil.example`, `javascript:` → must resolve to same-origin or reject. Implementation must parse with URL API and compare origin, never `startsWith`.
- **Sources:** RFC 9700 (rfc-editor.org/rfc/rfc9700); RFC 7636; RFC 9207; RFC 8707 (2020); CWE-601; MCP spec 2025-06-18, Basic → Authorization (modelcontextprotocol.io/specification/2025-06-18/basic/authorization).
- **Method:** **Continuous / per-request evaluation** — NIST SP 800-207 tenet: access granted per session and re-evaluated; **OpenID CAEP 1.0** (Final Specification approved Sept 2025 together with Shared Signals Framework 1.0 and RISC 1.0; spec document dated 29 Aug 2025) for propagating revocation/session-change events. Short-lived access tokens + refresh with re-check (RFC 9700 recommends refresh-token rotation / sender-constraining for public clients). "Time-of-check to time-of-use" is CWE-367; copying an ACL at ingest without a re-sync path is the same class at data level.
- **When:** Before: for every credential or derived ACL, write down its **revocation path and max staleness** (design decision recorded in an ADR — Nygard, "Documenting Architecture Decisions", 2011). After: revocation test.
- **Sources:** NIST SP 800-207 (2020); OpenID CAEP 1.0 Final (openid.net/specs/openid-caep-1_0-final.html, 2025); RFC 9700; CWE-367; Nygard 2011.
- **Method:** Treat any regex over untrusted input as an algorithmic-complexity risk (CWE-1333 *Inefficient Regular Expression Complexity*; CWE-400). Prefer linear-time engines (Thompson NFA / RE2 — Cox, "Regular Expression Matching Can Be Simple And Fast", 2007; V8 experimental non-backtracking engine: `--enable-experimental-regexp-engine` enables the `l` ("linear") flag, `--enable-experimental-regexp_engine-on-excessive-backtracks` adds automatic fallback; V8 v8.8, v8.dev blog 11 Jan 2021; experimental, behind flags, not on by default in Node/browsers); bound input length before matching; avoid nested quantifiers and ambiguous alternation. Empirical basis: Davis, Coghlan, Servant & Lee, *The Impact of ReDoS in Practice*, ESEC/FSE 2018 (thousands of super-linear regexes across >10k npm/pypi modules; developers usually fix by rewriting the regex).
- **Sources:** CWE-1333; Davis et al. FSE 2018 (doi 10.1145/3236024.3236027); Cox 2007 (swtch.com/~rsc/regexp/regexp1.html); v8.dev/blog/non-backtracking-regexp.
- **Method:** **Secure by default** — the product is safe with zero configuration (CISA and partners, Apr 2023; revised 25 Oct 2023). **Fail-safe defaults / least privilege** (Saltzer & Schroeder 1975). Attack-surface reduction: inventory every listener and endpoint (Howard, Pincus & Wing, "Measuring Relative Attack Surfaces", 2003). Prometheus's own security model (prometheus.io/docs/operating/security) states the opposite of a trust assumption: "It is presumed that untrusted users have access to the Prometheus HTTP endpoint and logs", and that these HTTP endpoints "should not be exposed to publicly accessible networks like the internet" without appropriate measures — i.e. whatever a metrics endpoint exposes must be treated as readable by untrusted parties unless the operator adds network/auth controls. Containers: bind dev services to `127.0.0.1`, not `0.0.0.0`.
- **Sources:** CISA *Secure by Design* (cisa.gov/resources-tools/resources/secure-by-design, Apr 2023, rev. Oct 2023); Saltzer & Schroeder 1975; Howard, Pincus & Wing 2003 (PDF at cs.columbia.edu/~wing/publications/Howard-Wing03.pdf); Prometheus security model page; OWASP ASVS 5.0.
- **Method:** Same as #2 at the **token-scope** layer: every protected-resource handler checks scope (RFC 6750 §3.1 `insufficient_scope`; RFC 9700 recommends restricting token privileges to minimum). Agent-specific: OWASP Top 10 for LLM Applications 2025 **LLM06 Excessive Agency** (excessive functionality/permissions in tools). Structural fix: gate at the dispatcher (all tools pass one scope check keyed by a declared `requiredScope` per tool) so a new path cannot be added ungated.
- **Sources:** RFC 6750 (2012); RFC 9700; OWASP Top 10 for LLM Applications 2025 (genai.owasp.org); MCP authorization spec 2025-06-18 (error table: 403 for invalid scopes / insufficient permissions).
- **Method:** Secrets never leave the secret store in plaintext: store-referenced injection (Twelve-Factor "Config", Wiggins 2011, + encrypted-at-rest files), pre-commit and pre-share secret scanning, short-lived credentials so leaks expire. Evidence of scale: Meli, McNiece & Reaves, *How Bad Can It Git?*, NDSS 2019 (>100k repos leaking; thousands of new unique secrets/day; only 19% of detected secrets were removed within ~2 weeks, so 81% persisted — and removal from HEAD does not remove them from history). SSDF PS.1 "protect all forms of code from unauthorized access and tampering" and PO.5 secure environments. For agents: Anthropic Claude Code security docs advise permission/deny rules for reading sensitive files [docs.anthropic.com — not re-opened]; OWASP LLM Top 10 2025 **LLM02 Sensitive Information Disclosure**.
- **Sources:** Meli et al. NDSS 2019; NIST SP 800-218 (2022); Twelve-Factor App (12factor.net, 2011); OWASP LLM Top 10 2025; Gitleaks / TruffleHog official READMEs.
- **Method:** **Shift-left, per-change review**: SSDF PW.7 "Review and/or analyze human-readable code to identify vulnerabilities" applied per change, PW.8 test executable code; Microsoft SDL (threat model per feature, security review gate). Make findings actionable at code-review time — Sadowski et al., "Lessons from Building Static Analysis Tools at Google", CACM 61(4), 2018 (tools must run in the review workflow; "effective false positive" rate kept low or devs ignore them); Bessey et al., "A Few Billion Lines of Code Later", CACM 2010. Small batches reduce review defect escape — Cisco/SmartBear study: review effectiveness drops beyond ~200–400 LOC per session (Cohen, *Best Kept Secrets of Peer Code Review*, 2006 — a vendor-published book, not peer-reviewed) **[unverified figure]**. Process: checklist at the gate (Gawande, *The Checklist Manifesto*, 2009); pre-mortem before building auth-touching features (Klein, HBR, Sept 2007).
- **Sources:** NIST SP 800-218 v1.1 (Feb 2022); Microsoft SDL (microsoft.com/securityengineering/sdl); Sadowski et al. CACM 2018 (doi 10.1145/3188720); Bessey et al. CACM 53(2) 2010; Gawande 2009; Klein 2007.
