# Sources: Machine resources: RAM, processes, browsers, waits

Carried over from the research pass of 2026-10-25 (`02-research-machine-resources.md`), product-specific lines removed. Each line keeps the tag it had there: **[V]** checked against the primary page in that pass; **[K]**, **[B]**, **[C]** or **[M]** a known citation (author, year, venue) not re-opened; **[U]** unverified, treat as a hypothesis. Lines without a tag were cited with their venue and date only.

- **Little's law** (J. D. C. Little, "A Proof for the Queuing Formula L = λW", *Operations Research* 9(3), 1961) [K]: items in system = arrival rate × time in system. Peak RAM ≈ Σ (concurrent jobs × RSS per job). Long-lived jobs (dev servers left up, agents running 3 h) raise L exactly as much as more arrivals do.
- **USE method** (Brendan Gregg, "Thinking Methodically about Performance", *ACM Queue*, 2012; CACM 2013) [V]: for every resource check Utilization, Saturation, Errors. Gregg's generic memory row [V]: utilization = available free memory, saturation = anonymous paging / swapping, errors = failed `malloc()`. Our mapping for this machine (not his wording): utilization = committed bytes / commit limit; saturation = paging / PSI stall; errors = OOM kills, allocation failures, crashes.
- **Google SRE book, "Addressing Cascading Failures"** (Beyer et al., O'Reilly, 2016) [V]: "more in-flight requests consume more RAM"; "it is usually better to have small queue lengths relative to the thread pool size"; "Servers should protect themselves from becoming overloaded and crashing"; set and propagate deadlines; "Always use randomized exponential backoff"; "Limit retries per request."
- **Release It!** (Michael Nygard, Pragmatic Bookshelf, 2007; 2nd ed. 2018) [K]: stability patterns *Timeouts*, *Bulkheads*, *Circuit Breaker*, *Fail Fast*, *Steady State* (every resource that accumulates must have a purge mechanism) — Steady State is the named pattern behind failures 3 and 5.
- **Pre-mortem** (Gary Klein, "Performing a Project Premortem", *HBR* 85(9), Sept 2007) [V, citation only]: before starting, assume the run crashed the machine and list why.
- **The Checklist Manifesto** (Atul Gawande, 2009) [K]: short DO-CONFIRM checklists at pause points (before launch, before finish).
- **Method:** make the safe path the only path — mandatory mediation (Saltzer & Schroeder, "The Protection of Information in Computer Systems", *Proc. IEEE*, 1975: *complete mediation*) [K]; poka-yoke (Shingo, 1986) [K]. Advisory locks only work if every caller takes them, so enforce at the tool boundary (pre-exec hook), not in prose.
- **Method:** resource lifetime bound to an owner (RAII, Stroustrup, *The C++ Programming Language*, 1985+; Python `with`, PEP 343, 2005 [K]); kill the **group/tree**, not the PID; Nygard *Steady State*.
- Memory cap at start: Next.js documents memory levers (`next build --experimental-debug-memory-usage`, disabling source maps, `experimental.preloadEntriesOnStart: false` for the server, `experimental.webpackMemoryOptimizations` — mostly build-time; the webpack-specific ones do not apply to Turbopack) [V nextjs.org "How to optimize memory usage", lastUpdated 2026-04-28]; the page gives no dev-server memory figures, so "5–12 GB" is our observation, not Next.js's; cap the heap with `NODE_OPTIONS=--max-old-space-size=4096`.
- Every install has a timeout (SRE / AWS Builders' Library: "set a timeout on any remote call" [V, Marc Brooker, 2019]); on timeout kill the tree (F3) and retry with exponential backoff + jitter, bounded attempts [V].
- **Method:** shared service vs per-client process; fixed cost × N sessions is a capacity line item. MCP spec 2025-06-18 [V]: with **stdio**, "The client launches the MCP server as a subprocess" (so every client that connects launches its own server process — our inference; the spec does not say "per session"); with **Streamable HTTP**, "the server operates as an independent process that can handle multiple client connections" (one shared process; spec: servers MUST validate `Origin`, and SHOULD bind only to localhost when local).
- **Method:** explicit stopping conditions and effort scaling. Anthropic, "Building effective agents" (19 Dec 2024) [V]: "include stopping conditions (such as a maximum number of iterations) to maintain control"; start with the simplest solution. Anthropic, "How we built our multi-agent research system" (13 June 2025) [V]: effort scaled to complexity ("Simple fact-finding requires just 1 agent with 3-10 tool calls"; "direct comparisons might need 2-4 subagents with 10-15 calls each"; "complex research might use more than 10 subagents"), an early failure was "spawning 50 subagents for simple queries", and "multi-agent systems use about 15× more tokens than chats". SRE deadlines [V]: every unit of work has a deadline, propagated to children. Timeboxing (Scrum/agile practice) [K].
- **Method:** event-driven waiting; polling only as a bounded fallback. Martin Fowler, "Eradicating Non-Determinism in Tests" (14 Apr 2011) [V]: "Never use bare sleeps to wait for asynchonous responses: use a callback or polling"; callbacks are best; polling with a short interval and a high, explicit timeout otherwise. Retries/back-off with jitter (AWS Builders' Library, Brooker 2019 [V]; SRE book [V]).
- Errors - Event Log (Resource-Exhaustion-Detector, ID 2004) [U] - `dmesg - grep -i oom`, `memory.events` (cgroup) - exit code 137 = 128+SIGKILL on Linux/containers (often, not always, the OOM killer); Node "JavaScript heap out of memory" when the heap cap is hit
